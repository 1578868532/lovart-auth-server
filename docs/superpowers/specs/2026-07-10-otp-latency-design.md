# OTP 收取延迟优化设计

## 目标与边界

本设计仅优化服务端从受控收件箱发现新邮件、匹配并向已授权桌面客户端返回结果的延迟和可靠性。

- 目标：在邮件已送达 `INBOX` 后，常态下 1–3 秒内可用；服务断线后自动恢复且不遗漏基线后的邮件。
- 不保证上游发件方的投递时间；其投递延迟不计入上述目标。
- 不改变许可证校验、目标邮箱匹配、验证码一次性消费或桌面本地中继接口。
- 不读取旧邮件，不返回基线前的验证码，不记录验证码明文。

## 已确认的现状

当前部署的云端服务每次轮询会连接 IMAP、从最新邮件向前逐封下载并解析最多 35 封完整邮件。线上观测到一次轮询约为 20 秒。客户端已在触发“发送验证码”前调用基线接口，但服务端基线只有本地时间戳；随后请求仍会触发完整扫描。IMAP 连接错误被转为 `waiting`，客户端无法分辨邮件尚未到达和邮件服务失败。

## 方案选择

采用“UID 增量扫描 + IMAP IDLE + 低频兜底轮询”组合。

1. **UID 基线**：基线接口连接邮箱、记录当前 `uidValidity` 与 `uidNext - 1`。该值定义本次验证码请求可接受的最小新邮件 UID。
2. **IDLE 长连接**：后台保持单个 IMAP 连接并监听新邮件事件。收到事件后，只处理 UID 高于未完成请求最低基线的邮件。
3. **兜底扫描**：IDLE 断线、重连、服务启动或周期性校验时，仅搜索上次处理 UID 之后的邮件。永远不再以“最近 N 封完整邮件”为主路径。
4. **分层读取**：先取得 UID、日期、发件人、收件人和主题；只有初筛命中的新增邮件才下载正文并解析验证码。

此方案优于只缩短轮询间隔：IDLE 缩短邮件到达后的发现时间，UID 水位线保证不误取旧邮件，轮询和增量搜索保证断线时仍可追补。

## 数据与状态

每个待处理 OTP 请求保存：

```text
requestId
targetEmail
machineId
createdAt
baselineUidValidity
baselineUid
status: pending | success | expired | failed
lastErrorCode
```

服务进程保存每个邮箱的 `lastProcessedUid` 和 `uidValidity`。`uidValidity` 改变时，清空 UID 游标、重新建立请求基线；绝不把旧 UID 空间中的邮件视为新邮件。

请求匹配规则：邮件 UID 必须严格大于该请求的 `baselineUid`，并且邮件到达时间不早于请求建立时间的合理容差；之后沿用现有发件人、主题、收件人和正文匹配规则。验证码被匹配后立即一次性消费。

## 时序

```text
桌面客户端       OTP 服务                IMAP
    | 建立基线       |                      |
    |-------------->| 查询 uidNext         |
    |<--------------| 返回基线 UID          |
    | 触发发码       |                      |
    |                |<---- IDLE 新邮件 ----|
    | 获取验证码     | 读取新增 UID 头部    |
    |-------------->| 仅解析候选正文        |
    |<--------------| success / waiting / error
```

客户端必须在基线成功后才触发发码。若基线建立失败，禁止继续发送并向用户显示可重试的服务错误，避免失去“只接收新邮件”的边界。

## 错误处理与恢复

服务端返回稳定错误码，桌面端据此显示明确状态：

| 场景 | 服务端状态 | 客户端提示 |
|---|---|---|
| 邮件尚未到达 | `waiting` | 正在等待新邮件 |
| IMAP 鉴权失败 | `imap_auth_failed` | 邮箱授权配置异常 |
| 代理连接失败 | `imap_proxy_failed` | 邮箱代理不可用 |
| TLS/网络超时 | `imap_network_failed` | 邮箱连接超时，正在重试 |
| 筛选未命中 | `waiting` + 诊断计数 | 已收到新邮件但未匹配验证码 |
| 请求过期 | `expired` | 验证码等待超时，请重新发送 |

IDLE 连接断开后采用有上限的指数退避重连；每次重连成功后执行 UID 增量补扫。兜底任务每 10 秒检查连接健康；若连接异常则重连并补扫，而不是并发创建第二个扫描器。

## 安全与可观测性

- 不在日志中写入验证码明文、完整邮箱或代理地址；仅记录哈希/掩码、UID、耗时、错误码和匹配阶段。
- `/api/otp/status` 改为管理员鉴权，并只返回脱敏配置状态和聚合指标。
- 状态指标至少包括：IDLE 已连接、最近事件时间、最近增量扫描耗时、每阶段过滤数量、重连次数、最近错误码及是否启用代理。
- 代理配置只存在云端环境变量中；桌面端浏览器代理设置不影响云端 IMAP 连接。

## 兼容与迁移

保留现有 `/api/otp/mark-baseline` 和 `/api/otp/get` 路径及授权方式。基线接口增加 UID 快照；响应可附带不敏感的 `requestId` 和 `baselineReady`。旧桌面版本若未消费新字段，仍能工作；新桌面版本应在基线失败时终止发码流程并展示错误。

以 `lovart-auth-server-git` 作为唯一可部署源，停止手工修改不受 Git 管理的 `lovart-auth-server` 副本。桌面变更和服务端变更在同一发布周期验证。

## 验收与测试

1. 单元测试：UID 基线比较、UIDVALIDITY 变更、旧验证码拒绝、一次性消费、错误码映射。
2. IMAP 适配器测试：模拟 IDLE 新邮件、断线重连、增量补扫和空邮箱。
3. 集成测试：建立基线后插入旧邮件和新邮件，仅新邮件可匹配；连续多封新邮件中目标邮件能在 3 秒内返回。
4. 故障测试：错误代理、错误授权码、超时均不能被返回为 `waiting`。
5. 发布验证：部署后执行一次受控测试，记录从邮件到达 INBOX 至接口返回的 p50/p95；目标 p50 不高于 3 秒，p95 不高于 8 秒（不含上游投递时间）。

## 非目标

- 改变上游邮件发送速度。
- 规避发件方的验证、访问控制或风控。
- 将邮箱凭据移入桌面应用。
